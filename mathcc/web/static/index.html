Evidence

  • On 20,000 random inputs per expression, the guarded compiler gave 0 wrong results. A typical unguarded simplifier gave 339, 9,831 and 286 wrong results on three of the demo expressions.
  • More than 5,000 randomly generated expressions were compiled and compared with the originals on the final version, and many more during development. The comparisons found real bugs along the way, all fixed.
  • Compiled code ran 2 to 28 times faster than a plain tree-walking evaluator on the demo expressions.
  • Every rewrite is logged and re-tested by a separate checker that also looks for a counterexample with the guard removed, so each run-time check is shown to be necessary.

What is new in this project

Simplifying an expression is easy. Simplifying it without quietly changing what it computes is the hard part.

The problem

Every algebra system applies rules such as x/x = 1. These rules are true on paper, but a computer evaluates the original expression on real numbers, and at some inputs the original and the simplified form disagree.

Common rewriteFails whenWhat this compiler does
x/x → 1x = 0: the original is undefined (NaN)Adds the condition x ≠ 0
sqrt(x²) → xx < 0: the answer is -xRewrites to abs(x), which is always right
sqrt(z)·sqrt(z) → zz < 0: the original is NaNAdds the condition z ≥ 0
ln(exp(x)) → xexp(x) overflows or underflowsAdds the condition that exp(x) is finite and not zero

How the compiler decides

Every sub-expression carries three facts: a range of possible values, whether zero is excluded, and whether it is certainly a finite number. They come from your assume lines. Each rewrite states the condition it needs and the compiler decides one of three ways.

The four new parts

1. Guarded rewriting with run-time fallback

Idea. A rewrite carries a condition about any sub-expression, not just a variable. If the assumptions prove the condition, the rewrite is free. If not, the condition becomes an extra output of the compiled program. When it is false at run time, the program evaluates the original expression, so the result is always the same as the original.

Example. (w+1)/(w+1) becomes 1 with the check w + 1 ≠ 0. At w = -1 the check fails and the program returns NaN, like the original.

Evidence. 0 wrong results against the original over 20,000 inputs per expression, where the classic approach is wrong thousands of times.

src/simplify.hpp, src/backend.hpp

2. Rewrites that check themselves

Idea. Every rewrite is recorded as before, after, and the conditions it relied on. A separate checker samples inputs that satisfy those conditions and confirms before and after agree, including NaN. It then removes each run-time condition and looks for an input where the rewrite breaks, which shows the condition is necessary.

Example. For x*x/x → x it reports: with the guard dropped, at x = 0 the result is 0 but the original gives NaN.

Evidence. On the demo, 12 of 12 steps verified and 3 of 3 conditional steps have a concrete counterexample.

src/analysis.hpp: certify

3. Accuracy-aware choice of form

Idea. Some equal expressions lose accuracy on a computer. The compiler tries stable equivalents and measures each one against a higher-precision evaluation, then keeps the more accurate form unless it costs much more.

Example. exp(x) - 1 becomes expm1(x), and 1 - cos x becomes 2 sin²(x/2). The worst relative error falls from about 1e-4 to 5e-8 for the second one.

src/simplify.hpp: stab, src/analysis.hpp: measuredError

4. Finding new rules, with their conditions

Idea. The compiler enumerates about 18,000 small expressions and groups those that behave the same on a region of inputs: everywhere, x ≠ 0, x ≥ 0, x > 0 or x < 0. A pair that agrees only on a region becomes a rule with that region as its side condition. Each rule is re-tested on fresh inputs.

Example. It found 2·ln(x) = ln(x·x) when x ≥ 0, which is a weaker condition than the one the simplifier used before.

src/analysis.hpp: discoverRules

How it compares with existing work

Existing workWhat it doesWhat it does not do
REDUCE GUARDIANComputes degenerate cases as guarded expressionsStays symbolic; does not produce executable code with a fallback
Maple, Mathematica, MATLAB assumeUse assumptions to simplify furtherDrop degenerate cases silently when assumptions are missing
HerbieImproves floating-point accuracy by searching equivalent formsIts rewrite rules were historically unsound; it does not give a fallback guarantee
RulerInfers rewrite rules automaticallyDoes not attach inferred side conditions in the way part 4 does

The distinct contribution is the combination in one small compiler: conditions proven from facts when possible, a run-time check with exact fallback otherwise, a checker that tests every step, and accuracy-aware selection.

What is not claimed

  • The checks are randomised tests. They are strong evidence, not a formal proof.
  • The compiler is not an e-graph. It rewrites in one pass.
  • Results equal the original in IEEE double precision, with stated exceptions: inputs are finite, +0 and -0 are treated as equal, and equivalent forms may differ by a few units in the last place.
  • It does not expand or factor polynomials, so (x²−1)/(x−1) is left alone.
Patents. Each idea above has related published work, so this project cannot be assumed to be patentable. India's Patents Act (Section 3(k)) excludes computer programs and algorithms as such. A prior-art search by a patent attorney would be needed before any claim. A paper at a compilers or floating-point workshop is the more realistic next step.

Bugs the testing found

A random-expression tester compiled thousands of expressions and compared each with its original. It found real mistakes in early versions, which are now fixed:

  • Merging fractional powers was unsound at negative infinity, so it now requires x ≥ 0.
  • A zero coefficient dropped the other factors, turning 0·ln z into 0 even for z < 0.
  • ln(exp y) → y also needs exp y not to overflow or underflow.
  • x/x computed as x·(1/x) is not exactly 1 in floating point, so division is kept as division.

References and inspiration

This project sits between computer algebra and floating-point compilers. The works below are the closest prior work and the background for its design.

Each entry says how the project relates to it. The closest works were identified while checking what already exists, so they are listed as prior art and context.

Closest to this project

  • GUARDIAN: Guarded Expressions in Practice
    A. Dolzmann and T. Sturm. REDUCE computer algebra system manual, section 20.27.

    Closest prior idea. It observes that algebra systems turn x/x into 1 and drop the case x = 0, and proposes keeping the degenerate cases as guarded expressions. This project applies the same idea to generated code and adds a run-time fallback.

  • Herbie: Automatically Improving Accuracy for Floating Point Expressions
    P. Panchekha, A. Sanchez-Stern, J. R. Wilcox, Z. Tatlock. PLDI 2015.

    Accuracy part. Herbie compares candidate rewrites against high-precision evaluation and keeps the most accurate. The stable-form selection here uses the same measurement idea on a much smaller set of rewrites.

  • Better Together: Unifying Datalog and Equality Saturation
    Zhang et al. PLDI 2023. arXiv:2304.04332.

    Why conditions matter. It describes Herbie's unsound rewrite rules and shows rules that are only correct under conditions, for example a fraction rule that requires b ≠ 0, and uses interval analysis to make them sound. This supports using interval facts as the core of the design.

  • Rewrite Rule Inference Using Equality Saturation
    Nandi et al. OOPSLA 2021. arXiv:2108.10436. (Ruler)

    Rule discovery part. Ruler infers rewrite rules by enumerating terms and comparing their behavior. The discovery tool here uses the same enumerate-and-compare idea and adds regions of inputs, so a rule found on x ≥ 0 carries that condition.

  • egg: Fast and Extensible Equality Saturation
    M. Willsey et al. POPL 2021.

    Not used, but compared. Equality saturation explores many equal forms at once. This project rewrites in a single pass, which is simpler and faster to compile; an e-graph is listed as future work.

  • Target-Aware Implementation of Real Expressions
    arXiv:2410.14025.

    Cost-aware choice. It selects among equivalent implementations using a cost and accuracy model, as the stability step here does in miniature.

Background and related

  • Implicit assumptions: the dark side of computer algebra systems
    P. Holoborodko. Advanpix blog, 2017.

    Shows how symbolic engines make unstated assumptions about variables. A practical statement of the problem this project addresses.

  • Interval Arithmetic, Extended Numbers and Computer Algebra Systems
    Academia.edu.

    Discusses values for which x - x = 0 and x/x = 1 fail, such as infinity and NaN. The compiler tracks "certainly finite" for the same reason.

  • Simplifying products of fractional powers of powers
    arXiv:1203.1350.

    Treats when fractional powers can be combined. This is the topic behind the conditions on merging exponents such as sqrt(z)·sqrt(z).

  • What Every Computer Scientist Should Know About Floating-Point Arithmetic
    D. Goldberg. ACM Computing Surveys 23(1), 1991.

    The reference for cancellation, rounding and why equal expressions differ on a computer, which underlies the accuracy part.

  • Interval Analysis
    R. E. Moore. Prentice-Hall, 1966.

    The source of interval arithmetic, used here to prove conditions from assumptions.

  • Abstract interpretation: a unified lattice model for static analysis of programs
    P. Cousot and R. Cousot. POPL 1977.

    The framework behind attaching small facts (range, zero excluded, finite) to every node and propagating them.

  • Compilers: Principles, Techniques, and Tools
    A. Aho, M. Lam, R. Sethi, J. Ullman. 2nd edition, 2006.

    The course text for the phases used here: lexical analysis, parsing, semantic analysis, intermediate code, optimization and code generation.

The project

This is a compiler for mathematical expressions. You give it an expression and optional assumptions about the variables. It simplifies the expression symbolically, proves or checks the conditions each simplification depends on, and produces fast code that gives the same answer as the original expression, including where the original has no answer.

The course project covers every compiler phase. The part that goes beyond the course is described on the What is new page, and the work it builds on is on the References page.

Limits

  • Inputs are finite numbers, and overflow of addition and multiplication is ignored.
  • The compiler does not expand or factor polynomials.
  • Rewrite checks are randomised tests, not formal proofs.
